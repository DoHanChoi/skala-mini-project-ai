# A안 개발 기준: 근거를 검증하는 장애 진단 에이전트

작성일: 2026-10-20 (Asia/Seoul)

이 문서는 개발 시 참조할 목표·초기 설계·이슈 분할안이다. 문서 작성은 승인되었으며, 각 개발 이슈의 실행은 별도 승인을 받는다. 아래 초기 범위와 설계 기본값은 다음 착수 논의에서 변경할 수 있다. 기능 구현 완료를 의미하지 않는다.

## 1. 목표와 현재 상태

운영 담당자가 진단 답변에서 **관측 사실, 원인 가설, 권장 조치**를 구분하고, 사실에 연결된 수치와 출처를 직접 확인할 수 있게 한다.

기준 커밋: [`447db63`](https://github.com/DoHanChoi/skala-mini-project-ai/commit/447db631b079f6c8b5e67c3b2bfce4dbaf59169f).

| 항목 | 현재 | 개선 목표 |
|---|---|---|
| 모니터링 | 샘플 JSON + 무작위 수치 변동 | 운영 예제는 유지하고 평가 시 고정 스냅샷 사용 |
| 매뉴얼 | 키워드 규칙으로 유형 결정 후 Markdown 조회 | 같은 방식으로 수집하되 출처 식별 정보를 보존 |
| 답변 | 자유 텍스트, 사실만 쓰라는 프롬프트 | 관측 사실·가설·조치를 구조적으로 분리 |
| 검증 | 30자 이상, `1)` 포함 | 구조·시스템·수치·근거 연결 검사 |
| 재작성 | 최대 3회 후 강제 통과 | 최대 3회 작성 후에도 실패하면 검증 실패로 종료 |
| 스트리밍 | 검증 전 초안을 사용자에게 표시 | 진행 이벤트는 유지, 장애 답변 본문은 검증 종료 후 공개 |
| 근거 표시 | 문장 안의 설명 중심 | 사용자가 원본 값과 문서 출처를 열람 |

현재 흐름은 `route → plan → gate → research → replan_check → analysis → write → validate → finalize`다. 일반 대화는 별도 경로로 응답한다. 조사 결과는 `collected`에 저장되지만 매뉴얼 URI 등은 답변 검증에 충분한 구조로 보존되지 않는다.

관련 코드: [그래프](../agent/graph.py), [MCP 서버](../mcp_server.py), [API](../server.py), [채팅 화면](../web_chat.html).

## 2. 초기 구현 범위와 경계

### 포함할 기능

1. 요청별 수집 근거에 ID, 원본 종류, 대상, 조회 시각, 출처를 부여한다.
2. 관측 사실은 시스템·측정 항목·값·단위·근거 ID를 포함한 구조로 생성한다.
3. 코드로 근거 존재, 시스템 일치, 허용된 항목, 값·단위 일치를 검사한다.
4. 원인 가설과 권장 조치를 별도 표시하고 연결된 출처를 제공한다.
5. 실패한 검사를 구체적으로 전달해 재작성하며, 반복 실패를 성공으로 바꾸지 않는다.
6. 검증 전 장애 초안을 외부로 보내지 않고 최종 답변과 근거·검증 결과를 전달한다.
7. 고정 데이터 기반 단위·통합 테스트와 개선 전후 평가를 작성한다.

### 초기 범위에서 제외

- 벡터 DB, 임베딩, BM25, 하이브리드 검색, 리랭커.
- 로그 분석 전문 에이전트 등 멀티에이전트 확장.
- 실제 시스템 복구 명령, 사람 승인 후 조치 실행.
- 확인 질문과 장기 대화 메모리 개선, 장애 보고서 파일 내보내기.
- LLM-as-judge로 자유 문장 전체의 사실성·인과관계를 판정하는 기능.
- 기존 라우팅·대상 폴백·매뉴얼 선택 로직 전면 수정.
- 기존 실행 스크립트의 세션 삭제 등 관련 없는 결함 수정. 필요하면 별도 후보로 기록한다.

**검증의 의미:** 코드로 확인 가능한 구조화된 관측 사실과 출처 연결을 검사한다. 매뉴얼의 적절성, 가설의 인과관계, 조치의 효과까지 보장하지 않는다. 대상 폴백이 잘못된 경우 수집 근거에 맞는 답변도 사용자 의도와 어긋날 수 있으며, 이를 평가 한계로 공개한다.

## 3. 설계 기본값

### 3.1 근거 보존

- 기존 `collected`의 `source`·`data`를 보존하며 근거 메타데이터를 추가하거나 별도 모델로 정규화한다. 원본 값을 변경하지 않는다.
- 근거 ID는 요청 안에서 유일하고 재작성 중 고정된다. 병렬 완료 순서가 달라도 태스크 순서로 결정해 재현 가능하게 한다.
- 모니터링 근거는 시스템명, 조회 시각, 원본 CPU·메모리·상태·알림을 가진다.
- 매뉴얼 근거는 MCP 서버, 실제 요청 URI, 제목, 조회 시각, 본문을 가진다. 문서 버전이 없으면 원본 본문 해시로 스냅샷을 구분한다.
- `analysis` 결과는 모델이 만든 해석이다. 관측값을 증명하는 독립적인 원본 근거로 승격하지 않는다.
- 누락된 값은 0으로 채우지 않는다. `unknown` 응답의 0 값은 유효한 실측값으로 인용하지 않는다. 매뉴얼 없음 안내도 정상 매뉴얼 근거로 취급하지 않는다.

### 3.2 구조화된 답변과 검증

권장 개념 모델은 `Evidence`, `Observation`, `DiagnosisDraft`, `ValidationResult`다. 실제 이름과 최소 필드는 각 담당 이슈에서 확정하고 문서에 반영한다.

| 구분 | 표현 및 검사 |
|---|---|
| 관측 사실 | `system_name`, `metric`, `value`, `unit`, `evidence_id`의 구조화된 항목 |
| 원인 가설 | 가설 문장과 관련 근거 ID. 항상 추정으로 표시 |
| 권장 조치 | 조치 문장과 관련 근거 ID. 실행 완료로 표현하지 않음 |
| 검증 결과 | 통과/실패/일반 대화 비대상, 검사 범위, 시도 횟수, 항목별 오류 |

- 초기 자동 수치 검증 대상은 CPU·메모리 사용률, 시스템 상태다. 알림은 원문 표시 또는 원문 일치 인용만 지원한다. 알림 문장의 임의 수치 추출은 확장 범위다.
- 관측 사실의 사용자 표시 문장은 검증된 구조화 항목에서 코드가 렌더링한다. 별도 자유 텍스트가 검증을 우회해 사실 영역에 들어가지 않게 한다.
- 수치는 시스템·측정 항목·근거 ID를 함께 비교한다. 서로 다른 서버의 같은 숫자나 다른 측정 항목의 숫자를 통과시키지 않는다.
- `91`과 `91.0`은 숫자로 동등하게 취급한다. 단위는 모델에서 명시하고, 허용하지 않은 단위 변환·반올림을 임의로 허용하지 않는다.
- 존재하지 않거나 다른 요청에 속한 근거 ID, 누락·비정상 값, 잘못된 모델 출력 구조는 실패다.
- 가설·조치의 근거 ID가 존재하는지는 확인하지만, 연결한 문서가 해당 문장의 의미를 실제로 지지하는지는 초기 버전에서 자동 보장하지 않는다.
- 가설·조치에 단순히 출처가 붙었다는 이유로 “내용 검증 완료”라고 표시하지 않는다. 코드가 렌더링한 관측 사실에만 수치 일치 표시를 붙인다.
- 초안 구조 파싱 실패도 같은 작성 시도 예산에 포함한다. 초기 작성 포함 총 3회까지 수행하며 반복 실패 시 확인된 원본 사실과 검증 실패 안내를 코드로 생성한다. 실패한 가설·조치 초안은 게시하지 않는다.
- 운영상 예외·연결 실패는 사실 검증 실패와 구분한다. 기존 예외를 숨겨 성공 응답으로 바꾸지 않는다.

### 3.3 모델·API·화면

- `fake`, `ollama`, `openai`의 공통 구조화 출력 계약을 맞춘다. 기본 자동 테스트는 fake이며, 실모델 결과를 추정해 통과 처리하지 않는다.
- 일반 대화와 v1은 기존 동작을 유지한다. A안 검증은 v2 장애 경로에 적용하며, 미적용 경로에 검증 성공 표시를 붙이지 않는다.
- 기존 `/chat`의 `reply`, `events`, `metadata` 및 SSE `FinalAnswer.reply`, `[DONE]` 계약은 유지한다.
- 필요 필드는 추가 방식으로 제공한다: 구조화된 진단, 근거 목록, 검증 결과. 최종 필드명과 형태는 파이프라인 이슈에서 확정하고 API 테스트로 고정한다.
- `/chat`과 `/chat/stream`의 최종 진단·근거·검증 결과는 동등해야 한다.
- 장애 초안의 `AnswerToken` 전송과 최종 응답의 원시 프롬프트 전송을 막아 검증되지 않은 내용을 노출하지 않는다. 단계 진행 이벤트와 일반 대화 스트리밍은 유지한다.
- UI는 관측 사실, 원인 가설, 권장 조치, 검증 상태, 근거 펼쳐보기를 제공한다. 원문은 HTML로 실행하지 않고 텍스트로 안전하게 표시한다.
- 검증 결과는 “관측 사실의 수치·시스템·출처 연결 확인”처럼 검사 범위를 표시한다. 가설·조치는 의미 검증 대상이 아님을 구분한다.

## 5. 검증과 평가 기준

### 반드시 확인할 사례

- 정확한 CPU·메모리·상태와 유효한 출처를 가진 정상 초안.
- 관측값 91을 99로 변경, 시스템 바꾸기, CPU와 메모리 항목 바꾸기, 단위 오류.
- 존재하지 않는 출처, 다른 요청의 출처, 누락된 값, unknown 시스템.
- `91`/`91.0` 같은 동등한 값이 오탐 없이 통과하는지.
- 매뉴얼 없음 안내가 유효한 매뉴얼로 처리되지 않는지.
- 근거가 없는 사실·빈 진단·잘못된 구조가 정상 진단으로 통과하지 않는지.
- 첫 초안 오류 후 수정 성공, 총 3회 실패 후 실패 상태와 확인된 사실만 반환.
- 실패한 초안과 원시 프롬프트가 REST/SSE 최종 응답·사용자 화면·저장 대화에 남지 않는지. 진단용 trace는 사용자 공개 출력과 구분한다.
- REST/SSE 최종 데이터 동등성, `[DONE]` 종료, 일반 대화 회귀, v1 비대상 표시.
- 복수 시스템의 근거가 섞이지 않는지, 동일 요청 재작성에서 근거 ID가 유지되는지.

### 측정 방법

1. **검증기 시험:** 사람이 정답을 정한 정상·오류 초안 fixture로 오류 검출률과 정상 초안 오탐률을 측정한다. 초기 열거 사례는 전부 기대 결과와 일치해야 한다.
2. **파이프라인 시험:** 고정 수집 결과와 fake 응답으로 재작성·실패 종료·출력 차단을 검증한다. 이것을 실모델 품질 향상으로 보고하지 않는다.
3. **실모델 비교:** 같은 질문·근거·모델·설정으로 전후 답변을 생성하고 수치 일치율, 출처 연결률, 최종 실패율, 재작성 횟수, 전체 응답 시간을 측정한다. 모델 정보·실행 횟수·실행 조건을 함께 기록한다.
4. **평가 공정성:** 테스트 fixture는 외부 호출 없이 실행한다. 실제 모델용 평가 질문은 개발에 사용한 사례와 구분한다. 측정값의 분모와 미검증 가설·조치 영역을 명시한다.
5. **비용 표기:** 기존 `cost_usd`는 가상 단가 기반이므로 실제 청구 금액으로 보고하지 않는다. 토큰·호출 횟수·추정 비용을 구분한다.

현재 코드의 임의 수치 변동, 최초 의도적 재시도와 태스크 고정 지연은 전후 비교에서 같은 조건으로 적용하거나 동일하게 제거한 평가 환경을 명시한다. 기준 비교는 v1이 아니라 기준 커밋의 v2를 사용한다.
